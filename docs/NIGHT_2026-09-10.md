### (a) red_ahead 의 거리 조건 — **없다. 그것이 설계다**

[team_code/kr_rules.py:890](team_code/kr_rules.py#L890) `_red_ahead` 는
거리 조건이 아예 없다. 함수 독스트링이 명시한다:
"30 m 억제창(stopline_suppress_m)과 달리 **거리 조건이 없다**: 적신호면
100 m 밖에서도 회피하지 않는다." 근거는 2026-08-30 실측(대기열을 비켜 신호
위반이 될 뻔한 건)이다. SHIFT_HOLD 진입은
[kr_rules.py:2807](team_code/kr_rules.py#L2807) 의
`ot_span is not None and _red_ahead(planner) is not None` 뿐이라 **d_red 임계가
존재하지 않는다.** 거리 상한이 있는 변종 `_red_zone_d`(line 1028)는 있지만
SHIFT_HOLD 는 그 함수를 **쓰지 않는다**(주석에 명시).

→ 93 m 앞 정지선에 억제가 걸리는 것은 의도가 맞다. 그리고 **이 정지의 원인이
아니다.**

### 진짜 원인 — standoff 20.5 m 에서 크립이 매 틱 막힌다

v_target 0 을 만든 후보는 로그상 `route_end` 지만, 그 키에는 **standoff
프로파일이 합쳐져 있다** ([kr_rules.py:5489](team_code/kr_rules.py#L5489) —
`so < candidate` 로 같은 변수에 병합되고 로그 키는 `route_end` 하나다).
같은 틱 진단이 그 값을 그대로 보여준다:

```
standoff_d 20.5   standoff_id 2   standoff_v 0.0
creep_d 20.5      creep_standoff 22.0   creep_stop_m 7.0
so_creep false    creep_block "cause"        ← 189 s 내내 동일
```

`creep_block: 'cause'` 는 `_obstacle_cause` 가 거짓이라는 뜻이고, 거짓인 이유는
[kr_rules.py:2033](team_code/kr_rules.py#L2033):

```python
end_m = self.active_m if end_m is None else end_m       # active_m = 150
if self.last_d_end is not None and self.last_d_end <= end_m:
    return False                                        # route_end 유령차 사정권
```

이 주행의 `d_end` 는 **138.1 m** 다 (경로 `data/route.pkl` 총 578.6 m). 150 안이라
매 틱 거짓 → 크립이 영영 안 열린다.

**이 배제 폭이 틀렸다는 것은 이미 저장소가 알고 있다.** 같은 함수의 never_stall
경로는 2026-09-08 에 이미 좁혔고([kr_rules.py:2283](team_code/kr_rules.py#L2283)
주석), 그 근거가 그대로 여기에도 적용된다:

> `active_m` 은 유령차 **후보를 만드는 창**이지 "종점 때문에 서 있다" 는 뜻이
> 아니다 — 150 m 앞에서 선 것은 종점이 세운 게 아니다.

never_stall 만 `ns_end_m`(= `route_end.unlatch_m` 30) 으로 고쳤고, **크립
게이트는 150 을 그대로 쓰고 있었다.**

### (b) HOLD 탈출 조건 / never_stall 이 왜 안 떴나

탈출 조건은 두 개뿐이다 — `_red_ahead` 가 None 이 되거나(녹색),
`route_index > ot_span[1]`(span 통과). 앞차가 안 움직이면 **녹색이 와도
standoff 가 계속 0 을 준다** (위 표가 그것이다).

never_stall 은 `_obstacle_cause` 를 **좁은 창(30 m)** 으로 부르므로 종점 배제를
통과한다. 실제로 무장을 시도한다 — 로그에 `never_stall {state: ARMING}` 이 있다.
안 뜬 이유는 다른 것이다:

- `_ns_cause` 도 적신호를 배제한다 → **녹색 구간에만 시계가 돈다.**
- 무장 임계는 `never_stall.deadlock_max_s` = **20 s 연속**이다
  ([kr_rules.py:2388](team_code/kr_rules.py#L2388) `ns_ticks < ns_max_ticks`).
- 이 교차로의 녹색은 약 13 s 다. 실측 **최대 ns_s = 6.0 s** (456 ARMING 틱 전부
  단계 0). 황색으로 넘어가면 시계가 0 으로 리셋된다.

→ 신호가 주기적으로 도는 한 never_stall 은 **구조적으로 무장할 수 없다.**
`_obstacle_cause` 가 red_ahead 를 신호 계열로 배제한다는 지시안의 추측은
맞지만, 결정적인 것은 그 위의 **종점 배제(150 m)** 다.

## [2] 정지 차량을 신호 대기 줄로 오판 — 지시안의 (a)(c) 는 성립하지 않는다

### (a) 게이트가 좌측을 검사한 것이 아니다 — **두 칸 게이트는 정상 동작한다**

`reject` 는 `left:zone_no_through_lane` 이지만, 같은 틱의 **`rejects` 전수**가
답이다:

```
"rejects": ["right:occupied_mid@p1", "left:zone_no_through_lane@p1"]
"lane_plan": {"pick": "[128,6,-5]", "side": "right", "hops": 2, "armed": true}
```

**우측이 먼저 평가됐다.** `_side_pass` 의 `_order` 가 `lane_plan.side` 를 보고
순서를 바꾸는 것(2bdeeef)은 그대로 걸려 있다. `reject` 필드가 **마지막 side 의
라벨만** 남기는 것이 오해의 원인이다 (코드 주석에 명시된 성질이고, 그래서
`rejects` 리스트가 따로 있다).

그리고 우측 기각 사유 `occupied_mid` 는 **옳다** — 같은 틱 차로 지도가
중간 차로가 막혔다고 말한다:

```
free_run  (128,6,-3) 20.5  (128,6,-2) 21.0  (128,6,-4) 20.1  (128,6,-5) 80.0
blocked_by  (128,6,-4)→4   (128,6,-3)→3   (128,6,-2)→2
```

정지 차량 3 대가 **나란히** 서 있다. 두 칸 오른쪽(-5)은 비어 있지만 거기 가려면
중간 차로(-4)를 지나야 하고 그 차로는 20.1 m 앞이 막혀 있다. 램프(15.5 m) +
여유가 들어갈 자리가 없다. **시프트를 안 한 것이 맞다.**

→ 고칠 것은 로직이 아니라 **보고**다. `reject` 한 줄만 보면 반대쪽을 검사한
것처럼 읽힌다. `rejects` 를 먼저 보도록 이 문서에 남긴다.

### (c) 요청한 `queue_stale_release_enable` 은 **이미 구현돼 있다**

## (2) 실선 차로를 먼저 고른 이유 — `passable` 은 표시를 **안 본다**

사용자 가설 "passable 이 실선을 아는데" 는 **틀렸다**. `passable` 은 넷뿐이다:
존재 ∧ 같은 방향 ∧ 폭 ≥ min_width ∧ 교차로 아님. 실선 판정은 `_side_pass` 의
solid 게이트(`_dashed_ahead_m` + `dash_slack_m`)에만 있다.

→ `avoid_map.lane_map_prefer_dashed_enable` — 후보 순위에서 **free_run 다음**
으로 점선을 본다. **실선 후보를 빼지는 않는다** (게이트 2바퀴가 유일한 길인
경우를 잃지 않기 위해). 잣대는 게이트와 같은 함수를 그대로 쓴다.

## (1) pick → SHIFT 2.9 s — `shift_on_pick` 은 그 런에서 **꺼져 있었다**

| t | |
|---|---|
| 52.96 | id 3 최초 관측 — **speed 0.00**, 그 틱부터 `blocked_by` 에 있다 |
| 53.01 | pick `[2756,3,6]` |
| 54.41 | WAIT  obj_s 1.5  t_left 4.5  budget 1.5 |
| 55.81 | WAIT  obj_s 2.9  t_left 4.4  budget 0.1 |
| 55.91 | **WAIT_EXPIRED** → 시프트 |

내역: **1.50 s** (`_static_ok` = obj_static_s) + **1.45 s** (그 뒤 WAIT).
뒤를 연 것은 시간 예산이 **아니다** — `t_left < budget` 은 끝내 참이 안 된다
(standoff = 3·v 가 v 를 따라가 t_left 가 4.5 에 고정, budget 은 3.0 − obj_s 로
줄기만 한다). 결국 `obj_s ≥ wait_before_shift_s` 가 열었다.

**그 런에서 `lane_map_shift_on_pick_enable` 은 꺼져 있었다.** 근거: 2칸 폴백이
성립하려면 `_lm_hops('left')` 가 2 를 내야 하고, 그건 `_lm_fb_hops` 가 있어야
하며, 그 값은 **`_owns_shift()` 안에서만** 세팅된다(`_lm_second_side`).
따라서 owns_shift 는 켜져 있었고 — 그렇다면 `_static_ok` 가 참이 된 t 54.46 에
`on_pick` 이 열렸어야 한다. 안 열렸으므로 `shift_on_pick` 이 off 다.

→ 뒤의 1.45 s 는 `shift_on_pick` 이 이미 없앤다. 앞의 1.50 s 를 없애는 것이
`avoid_map.lane_map_static_on_pick_enable` — 지도가 정지로 세어 내 차로를
막은 것으로 판정한 객체는 관찰을 기다리지 않는다. 잣대는 지도와 같은 것
(`lane_map_static_v`). **범위는 `on_pick` 한 줄뿐** — `_static_ok` 자체는
standoff·큐·보행자가 같이 쓰므로 안 건드린다.

**로그에 스위치 상태가 안 남는다.** 이번에는 폴백 경로로 역산했지만, 다음부터
가리려면 런 시작 줄에 설정을 남기는 것이 맞다 (백로그).

## (5) avoid_speed 20 km/h 250 m — **그건 회피 상한이 아니다**

| 무엇 | 틱 | route_s | 길이 |
|---|---:|---|---:|
| v_target 이 정확히 20 km/h | 243 | 247.2 → 482.4 | **235.2 m** |
| ├ `lc_cap` (계획 차선변경 상한) | 81 | 247.2 → 284.3 | 37.1 m |
| └ `lane_map` 회피 상한 | 162 | 428.3 → 482.4 | 54.1 m |
| 회피 상한 후보가 **살아 있던** 구간 | 324 | 428.3 → 484.4 | 56.0 m |

두 상한이 **동시에 산 틱은 0**이다. 사용자가 본 rs 247 시작점은
`_lc_speed_cap` — 계획 차선변경 4연속 구간의 상한이고, 값이 같은 20 km/h 일
뿐 다른 기능이다. 그쪽은 S자·조향 포화·|t_off| 1.85 m(항목 3 중대 + 항목 6)를
막으려고 넣은 것이라 좁히면 그 감점이 돌아온다.

**회피 상한 자체는 과하지 않다.** 56 m 인데, 12.5 → 5.56 m/s 감속에만
`(12.5²−5.56²)/(2·1.5) = 41.7 m` 가 필요하다. 트리거를 "램프 시작 − v×2 s"
(= 25 m)로 좁히면 상한이 물리적으로 도달 불가능해져 급제동이 된다
(CLAUDE.md 확정 사실의 상한형 되먹임). **수정하지 않았다.**

해제 쪽도 좁힐 것이 없다 — 상한은 t 69.2(rs 484.4)에 이미 풀렸고 복귀 완료는
t 76.5(rs 549)다. 오히려 먼저 놓는다.

**"추가" 부분(최저속도 5.9 → 2.0)은 사실이고, (4) 가 원인이었다.** 시프트가
일찍 시작돼서가 아니라 복귀 차로 참조가 v_cap 을 1.12 까지 끌어내려서다.
(4) 를 켜면 시뮬 최저속도가 2.01 → 4.82 로 돌아온다.

# 09-10 오후 2차 — 신호 216 · 불필요한 복귀

## ★ 신호 216 오매핑 — **기각**. 오매핑이 아니다

가설의 전제가 **id 공간을 섞은 것**이다. OpenDRIVE 에서 signal id 와
controller id 는 **별개 네임스페이스**다.

| | 216 |
|---|---|
| **signal** 216 | road 1846, 정지선 s 22.8, signal_ids [212…217], controller [64, 65] |
| **controller** 216 | road 2756 sec 0 정지선 s 75.05 — signal_ids [672, 673, 674] |

로그의 `light_id` · `stop_ctrl_ids` 는 **controller** 축이다
([route.py:578](vtd_adapter/route.py#L578) `update_lights` 가
`lid in tl.controller_ids` 로 붙인다).

`junction_ctrl_map['82'] = {'2756,-1': [216], '2806,1': [215]}` — **216 은
junction 82 의 road 2756 진입 컨트롤러**, 곧 자차 자신의 진입 방향이다.
사용자가 지목한 "road 2756 의 실제 신호 672~674" 는 같은 정지선의 signal_ids 고,
216 은 그 정지선의 controller 다. 둘은 경쟁 관계가 아니라 한 쌍이다.

**(b) VTD 는 "자차의 다음 교차로 진입 컨트롤러" 만 보낸다.** 두 런 전체에서
9910 이 보낸 id 는 **191 과 216 둘뿐**이고, 자차 도로와 정확히 붙어 있다:

```
controller 191 → junction 75, 진입 road 2533   … 자차가 2533 에 있는 동안만 온다
controller 216 → junction 82, 진입 road 2756   … 자차가 2756 에 있는 동안만 온다
road 2765(중간)·junction 진입 후 → lights []
```

거리 무관하게 오지 않는다. 우리 쪽에서 다시 고를 필요가 없다.

**(c) 전수**: 컨트롤러가 붙은 정지선 356건 중 "다음 교차로 == 그 컨트롤러의
교차로" **349건**, 판정 불가(successor 에 교차로 없음) 7건, **불일치 0건**.
`light_ctrl_match` 도 1301 True / 190 None / **0 False**.

**(d) 수정 없음.** 억제·정지는 자차 진입 방향의 **진짜 적신호**에 대한 반응이다
(t 55.5 적색, 정지선 83.7 m). 따라서 **(1) no_accel_red 래칫의 우선순위는
내려가지 않는다** — 오매핑으로 부풀려진 것이 아니다.

## 불필요한 복귀 — 원인은 valid_entry_lanes 가 **비어 있는 것**

**(a)** 사용자 가설("경로 차로 하나만 들어 있다")은 빗나갔다. 실제 값:

```
seg 0  target 'pair'    turn 'straight'  lanes 4개  chosen (2533,0,6)   ← 채워져 있다
seg 2  target 'finish'  turn None        lanes []   chosen (2756,0,5)   ← **빈 리스트**
```

build_route 는 `pair` 세그먼트에는 여러 차로를 넣는다. 마지막 `finish`
세그먼트만 **아예 계산하지 않는다**.

**(b)** `no_return` 이 안 돈 이유는 "현재 차로 ∈ valid 가 거짓" 이 아니다 —
그런 판정 자체가 그 경로에 없다. `_lm_deadline_s` 와 `_lm_no_return_m` 이 둘 다
`target=='pair'` **이고** `lanes` 가 비어 있지 않을 때만 산다. 마지막
세그먼트는 둘 다 아니라 데드라인이 None 이고, `_lm_no_return_m` 은 첫 줄에서
`return None` 한다. 스위치는 켜져 있었지만 **구조적으로 죽어 있었다**.

**(e) 11 m 전에야 움직인 것이 아니라, 램프 끝이 교차로 안에 놓여 있었다.**

```
t 47.4  span 생성       [453.5, 567.3]   blocker 3
t 53.4  RETARGET 합집합  [453.5, 581.9]   blocker 4 (= 정지선 대기차)
        정지선 route_s 578.5 · 종료선 577.5
```

복귀 램프의 **끝**이 정지선 4.4 m·종료선 3.4 m 뒤다. 자차는 그 사이 적신호로
서 있다가(t 76~86 lane 3, t_off ≈ 0) 움직이는 순간 d_stop 6.7 → 5.5 m 에서
차로를 넘었다. 생성 시에는 `span_into_zone` 게이트가 `_next_stopzone_s` 를
보지만 **재타겟의 합집합(min/max)은 다시 보지 않는다**.

**(c) 수정 — 둘 다 제어기 파트에서 끝난다** (build_route 를 안 건드린다):

  · `lane_map_span_zone_clamp_enable` — span 끝을 `_next_stopzone_s` 로 자른다.
    자르기만 하고 늘리지 않는다.
  · `lane_map_valid_by_map_enable` — route.pkl 이 비었으면 **레인그래프에서**
    유도한다. laneLink 는 이미 `next` 에 있다. 정의는 build_route 와 같다 —
    경로가 쓰는 진출 도로로 이어지는 진입 차로 전부.
    실측: 자차 (2756,0,3) 기준 **{2, 3, 4, 5} 넷 다 유효**(전부 junction 82 를
    직진 통과해 2806 으로 간다). 자차가 이미 유효 차로면 데드라인 = 세그먼트 끝
    (= 복귀를 종료선까지 미룬다), 아니면 램프 길이만큼 앞당긴다.

**(d) 한계 — 정직하게**: 이 둘로 복귀가 **없어지지는 않는다**. span 끝이 곧
"원 경로로 돌아온 지점" 이라, 복귀를 완전히 없애려면 span 을 경로 끝까지 밀어야
하는데 그건 [1] 의 "span 이 영영 안 풀리는" 버그를 다시 만든다. 이번 수정의
효과는 **복귀 램프가 교차로 안에서 끝나지 않게 하는 것**(정지선 578.5 로 클램프,
3.4 m 앞당김)과 **마지막 세그먼트에서 no_return 이 실제로 동작하게 하는 것**이다.
